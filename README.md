# Charlie-Quiz

E2E-тест реєстраційного квізу allright.com на Playwright + TypeScript.
+ Додатково виконав Завдання 2 (те ж саме тільки за допомогою AI-агента)

Оскільки квіз під постійними змінами A/B-тестів, зробив універсальну структуру проходження, 
з динамічними кроками, очікуваннями, локаторами.
Реалізовано тільки smoke-тест для покриття найважливішої бізнес-логіки:
- створюється акаунт 
- і бронюється пробний урок. 

## Запуск

```bash
npm install
npx playwright install chromium

npm test                  
npx playwright test       
npx playwright show-report
npm run typecheck
```

За основу береться `BASE_URL` (за замовчуванням `https://stage.allright.com`).
Шляхи всередині застосунку — у `tests/config/routes.ts`.

## Структура

| Шлях | Призначення |
| --- | --- |
| `tests/quiz.spec.ts` | сам тест: реєстрація → бронювання → перевірки |
| `tests/page-objects/quizPage.ts` | визначення типу кроку, дії, очікування |
| `tests/page-objects/components/popupHandler.ts` | попапи, що з'являються в довільний момент |
| `tests/network/apiWatcher.ts` | фоновий збір статусів POST-запитів |
| `tests/fixtures/test.ts` | фікстури `testUser` і `api` |
| `tests/config/routes.ts`, `tests/network/endpoints.ts` | URL і ендпоінти |

## Що перевіряє

Два бізнес-результати, обидва по реальних відповідях бекенду:

- `POST /api/v1/users` → 200 — користувача створено;
- `POST /api/v1/lessons` → 200 — пробний урок заброньовано.

## Припущення

Поточна структура і реалізація побудовані на цих припущеннях.

**Типи кроків покривають те, що є зараз.** Кожен варіант кроку розпізнається і проходиться
за поточним виглядом квізу. Якщо А/Б-тест принесе новий тип кроку, його треба буде дописати
до наявних — тест впаде з `Unknown step type at step N` і покаже URL, який не пройде.

**Результат визначається статусами ендпоінтів і URL сторінок.** Створення акаунта — це
`POST /users` з 200, бронювання — `POST /lessons` з 200. Завершення воронки визначається за
URL: `/request-gotten` (квіз пройдено, бронювання попереду) або `/dashboard` (бронювання вже
відбулось кроком квізу).

**Очікування між кроками прив'язані до `page_view_events`.** Замість фіксованих пауз крок
вважається пройденим, коли спрацював цей запит або змінився `pathname`.

## Що зробив би далі

- **Чистка тестових даних після прогону** — зараз кожен прогін лишає на стенді створеного
  користувача і заброньований урок.
- **Негативні сценарії.** Реалізовано тільки основний воркфлоу проходження квізу. При
  достатній кількості часу — валідація полів, помилкові дані, повторні проходження.
- **Прогін у CI** на кожен PR і за таймером, з трейсами на кожне падіння.

# Завдання 2 — AI-агент `quiz-test`

Той самий сценарій, але без спеки: агент проходить квіз **живим браузером** через Playwright MCP.
Визначення агента — `variant2/.claude/agents/quiz-test.md`, деталі — у `variant2/README.md`.

## Запуск

```
/quiz-test
/quiz-test https://stage.allright.com/uk/app/sign-up/long/charlie/age-range
```

Без аргументу URL береться з `tests/config/routes.ts` (`BASE_URL` + `ROUTES.QUIZ_START`).
Потрібен MCP-сервер `playwright` — оголошений у `.mcp.json` у корені; після першого підтягування
конфіга сесію Claude Code треба перезапустити.

## Що робить

Проходить квіз **двічі** (кожен прогін — новий згенерований користувач, чиста сесія) найкоротшим
шляхом і перевіряє ті самі два бізнес-результати по реальних відповідях бекенду: акаунт створено
і пробний урок заброньовано. Ендпоінти не захардкоджені — результат зчитується за моментом дії,
origin застосунку, методом і статусом, тож зміна URL видно у звіті як дрейф, а не як падіння.

Прогін не мокається — акаунти і бронювання на стенді створюються справді.
